# 11 — 对话式交付模式（Conversation Mode，默认）

> 适用对象：**不懂开发、也不想操作 GitHub 的业务方**。
> 一句话：你只用自然语言对 DSH 说话；建任务单、写代码、测试、独立评审、合并、发布、交付报告全部由 DSH 在**后台**代做，最后用**人话**向你汇报。
> 上游：`00-OPERATING-MODEL.md`（G0–G7 门禁一个都不少）；下游：`07-DELIVERY-REPORT.md`（对话版交付报告）。

## 1. 目标与不变量

1. **业务方只做 3 件事（对话版）**：说清楚要什么；需要拍板时回答一句；说「验收通过 / 不通过」。
2. **不变量**：G0–G7、独立评审（新上下文）、CI、分支保护、证据协议**全部保留**，只是这些操作由 DSH 代理执行，业务方不直接碰。
3. **不变量**：不可逆动作、涉法务、涉凭据/权限、范围取舍、预算 → 必须回到业务方确认（`09-ESCALATION.md`）。
4. **核心承诺**：业务方**不需要打开 GitHub、不需要输入命令、不需要理解 PR/合并/发布**。对话就是操作界面。

## 2. 你只需要说人话（常用说法）

| 你想做的事 | 你可以直接说 | DSH 会在后台做什么 |
|---|---|---|
| 提一个新需求 | 「帮我做一个……，用来……」 | 建任务单（审计用）→ 澄清 1–3 个问题 → 立项 |
| 改上次的东西 | 「上次那个按钮/文档再改一下，改成……」 | 找到原任务单 → 新分支 → 实现 → 走同一套门禁 |
| 看进度 | 「现在到哪一步了？」 | 读后台任务单/CI/评审状态，用人话汇报 |
| 叫停 | 「先停掉」 | 中断当前工作、保留现场与产物，汇报已完成/未完成部分 |
| 发布新版本 | 「发一个新版本」 | 汇总变更 → 版本号 → 发布 → 给你发布说明 |
| 验收 | 「验收通过」/「不通过，因为……」 | 记录验收结论；不通过则开新一轮修复 |
| 问技术细节 | 「这是什么意思？」 | 用非开发语言解释，不要求你读代码 |

写法建议：**一次对话只提一个需求**；说清「给谁用、解决什么问题、怎样算成功」。其余细节 DSH 会问，不要自己勉强补技术方案。

## 3. DSH 在后台做什么（你不用看，仅作知情）

| 对话动作 | 后台对应门禁/制品 | 产物（审计凭证） |
|---|---|---|
| 你说需求 | G0 受理 + G1 澄清与 DoR | GitHub issue（对话内容 + 8 字段）；`.agentspec/issues/<n>/BRIEF.md` |
| 需求较大/有取舍 | G2 设计与 RFC | 设计说明或 RFC 文档 + 评审记录 |
| 开始实现 | G3 实现 | 隔离工作副本 + 分支 `agent/<n>-<slug>` + 提交 |
| 自动测试 | G4 验证 | 门禁命令 + 退出码 + 原始输出；独立验证记录 |
| 独立评审 | G5 评审 | 新上下文 reviewer 的 `VERDICT: APPROVE / REQUEST_CHANGES` |
| 合并 | G6 合并 | PR + CI 全绿 + 合并记录 |
| 发布与交付 | G7 发布 | GitHub Release + 交付报告（对话版） |

> 业务方看到的是**第 5 节的对话版交付报告**；上表的 issue/PR/Release 只是后台凭证，**不要求业务方打开**。

## 4. 一次需求的完整时序（示例对话）

```text
你：帮我做一个「自动检查文档里的链接是否失效」的小工具，每次发版前能跑。

DSH：收到。确认 3 件事（都是选择题）：
     1) 只查仓库内相对链接，还是也查外网链接？（建议：先只查仓库内，外网链接单独开关）
     2) 发现问题时要阻止发版，还是只警告？（建议：阻止）
     3) 需要多久内交付？（建议：本轮）

你：按建议来。

DSH：已立项（后台任务单 #23）。我开始实现，完成后会给你一份人话报告；
     中途只在需要你决定时出现。

……（后台：实现 → 自动测试 → 独立评审 → 合并 → 发布；你不需要操作）……

DSH：完成。一句话结果：现在发版前会自动检查文档链接，坏链接会阻止发版。
     怎么用：以后正常发版即可，不需要额外命令。
     验证：我用一份故意写坏的链接测过，确实被拦住；正常文档全部通过。
     已知限制：只查仓库内链接，外网链接暂不检查（需要的话下一轮加）。
     需要你决定：是否现在就把新版发出去？（是/否）
```

## 5. 交付报告（对话版，固定 5 段）

每次交付，DSH 用以下 5 段汇报；**不要求业务方看懂技术细节**：

1. **一句话结果**：你的场景现在能怎样了。
2. **怎么用**：最短的操作说明（通常 0–3 步；纯内部改动写「不需要你做任何事」）。
3. **我怎么验证的（人话）**：做过哪些检查、有没有故意使坏测试过、结论是什么。
4. **已知限制**：还没覆盖什么、什么情况下会不好用（诚实列出，不藏）。
5. **需要你决定 / 下一步**：需要你拍板的选择题，或「没有，等你验收」。

技术链接（PR、CI、Release）放在报告末尾作附录；业务方不看也不影响验收。

## 6. 什么时候 DSH 会回来问你（升级规则）

以下情况**必须**回到对话里确认（`09-ESCALATION.md`）：
- 不可逆操作（删数据、改历史、覆盖发布、改仓库可见性）；
- 涉及账号、权限、凭据、花钱、对外发布；
- 需求范围要做取舍（加功能 vs 延期 vs 砍需求）；
- 验收口径本身不清晰、或实现后发现原需求不成立。

不需要你决定的事（DSH 自行处理）：用什么库/怎么写代码/怎么测/怎么提交/分支怎么命名/文档放哪。
默认规则：可逆且低风险的事项，DSH 按最保守方案继续并在报告里说明；不可逆事项一律等你回复。

## 7. 记录与追溯（你不用管，但保证可查）

- 后台仍会创建 GitHub issue / PR / Release 作为**审计凭证**（合规、可回溯、可交接）；
- 过程证据保存在本机 `.agentspec/runs/<时间戳>/`（不进公开仓）；
- 跨会话续接：换一个会话也可以说「继续上次那个需求」；DSH 通过后台 issue 编号与交付报告恢复上下文，不依赖聊天记忆。

## 8. 安全边界（不会因为「对话式」而放松）

1. **门禁不削弱**：自动测试、独立评审、CI、分支保护照常执行；不通过就不合并。
2. **合并与发布由 DSH 代操作**：前提是门禁全绿 + 独立评审通过；**发布前会在对话里告知你**。
3. **不碰凭据**：你不需要提供 GitHub token；本机已登录的 `gh` 凭据只在本地使用，不写进对话或仓库。
4. **隐私**：你的对话内容不会原样公开；写进公开任务单的只有必要的业务描述，且经过去敏。
5. **规则文件保护**：`.github/**`、`agents/**`、`docs/process/**` 的修改需要你**明确同意**（对话里说「可以」即可，不需要 GitHub review）。

## 9. 与开发者模式的关系

| 模式 | 适用人 | 入口 | 说明 |
|---|---|---|---|
| **A 对话式（默认）** | 业务方、不懂开发的决策者 | 直接和 DSH 对话 | 本文件 |
| **B issue 式** | 开发者、贡献者、外部社区 | GitHub issue 表单 + `agent:ready` | `01-REQUIREMENT-INTAKE.md` |

两种模式共用同一后台（G0–G7、角色、CI、orchestrator）；对话式只是把「写 issue/看 PR/合并」这些机械动作交给 DSH 代办。

## 10. 反模式（别这样做）

- ❌ 在对话里贴密钥、密码、个人隐私信息 → 不要贴；需要时用本机配置。
- ❌ 一句话塞 5 个不相关需求 → 拆开说，DSH 会一次只推进一个。
- ❌ 一边让 DSH 做，一边自己手改仓库 → 会产生冲突；要改就说出来，让流程处理。
- ❌ 把「代码能跑」当成「业务目标达成」→ 验收看的是第 5 节报告里的结果与限制。
- ❌ 要求跳过测试/评审直接上线 → DSH 会拒绝并说明原因（门禁是保护你的）。
