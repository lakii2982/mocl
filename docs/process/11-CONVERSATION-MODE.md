# 11 — 对话式交付模式（Conversation Mode，默认）

> 适用对象：**不懂开发、也不想操作 GitHub 的业务方**。
> 一句话：你只用自然语言对 DSH 说话；建任务单、写代码、测试、独立评审、合并、发布、交付报告全部由 DSH 在**后台**代做，最后用**人话**向你汇报。
> 上游：`00-OPERATING-MODEL.md`（G0–G7 门禁一个都不少）；下游：`07-DELIVERY-REPORT.md`（**完整技术版**交付报告；对话摘要见本文 §5）。

## 1. 目标与不变量

1. **业务方只做 3 件事（对话版）**：说清楚要什么；需要拍板时回答一句；说「验收通过 / 不通过」。
2. **不变量**：G0–G7、独立评审（新上下文）、CI、分支保护、证据协议**全部保留**，只是这些操作由 DSH 代理执行，业务方不直接碰。
3. **不变量**：不可逆动作、涉法务、涉凭据/权限、范围取舍、预算 → 必须回到业务方确认（`09-ESCALATION.md`）。
4. **核心承诺**：业务方**不需要打开 GitHub、不需要输入命令、不需要理解 PR/合并/发布**。对话就是操作界面。

## 2. 你只需要说人话（常用说法）

| 你想做的事 | 你可以直接说 | DSH 会在后台做什么 |
|---|---|---|
| 提一个新需求 | 「帮我做一个……，用来……」 | 建任务单（审计用）→ 澄清 1–3 个问题 → 立项 |
| 改上次的东西 | 「上次那个按钮/文档再改一下，改成……」 | 找到原任务单 → 新分支 → 实现 → 走同一套门禁 |
| 看进度 | 「现在到哪一步了？」 | 读后台任务单/CI/评审状态，用人话汇报 |
| 叫停 | 「先停掉」 | 中断当前工作、保留现场与产物，汇报已完成/未完成部分 |
| 发布新版本 | 「发一个新版本」 | 汇总变更 → 版本号 → 发布 → 给你发布说明 |
| 验收 | 「验收通过」/「不通过，因为……」 | 记录验收结论；不通过则开新一轮修复 |
| 问技术细节 | 「这是什么意思？」 | 用非开发语言解释，不要求你读代码 |

写法建议：**一次对话只提一个需求**；说清「给谁用、解决什么问题、怎样算成功」。其余细节 DSH 会问，不要自己勉强补技术方案。

## 3. DSH 在后台做什么（你不用看，仅作知情）

| 对话动作 | 后台对应门禁/制品 | 产物（审计凭证） |
|---|---|---|
| 你说需求 | G0 受理 + G1 澄清与 DoR | GitHub issue（对话内容 + 8 字段）；`.agentspec/issues/<n>/BRIEF.md` |
| 需求较大/有取舍 | G2 设计与 RFC | 设计说明或 RFC 文档 + 评审记录 |
| 开始实现 | G3 实现 | 隔离工作副本 + 分支 `agent/<n>-<slug>` + 提交 |
| 自动测试 | G4 验证 | 门禁命令 + 退出码 + 原始输出；独立验证记录 |
| 独立评审 | G5 评审 | 新上下文 reviewer 的 `VERDICT: APPROVE / REQUEST_CHANGES` |
| 合并 | G6 合并 | PR + CI 全绿 + 合并记录 |
| 发布与交付 | G7 发布 | GitHub Release + 交付报告（对话版） |

> 业务方看到的是**第 5 节的对话版交付报告**；上表的 issue/PR/Release 只是后台凭证，**不要求业务方打开**。

## 4. 一次需求的完整时序（示例对话）

```text
你：帮我做一个「自动检查文档里的链接是否失效」的小工具，每次发版前能跑。

DSH：收到。确认 3 件事（都是选择题）：
     1) 只查仓库内相对链接，还是也查外网链接？（建议：先只查仓库内，外网链接单独开关）
     2) 发现问题时要阻止发版，还是只警告？（建议：阻止）
     3) 需要多久内交付？（建议：本轮）

你：按建议来。

DSH：已立项（后台任务单 #23）。我开始实现，完成后会给你一份人话报告；
     中途只在需要你决定时出现。

……（后台：实现 → 自动测试 → 独立评审 → 合并 → 发布；你不需要操作）……

DSH：完成。一句话结果：现在发版前会自动检查文档链接，坏链接会阻止发版。
     怎么用：以后正常发版即可，不需要额外命令。
     验证：我用一份故意写坏的链接测过，确实被拦住；正常文档全部通过。
     已知限制：只查仓库内链接，外网链接暂不检查（需要的话下一轮加）。
     需要你决定：是否现在就把新版发出去？（是/否）
```

## 5. 交付报告（对话版，固定 5 段）

每次交付，DSH 用以下 5 段汇报；**不要求业务方看懂技术细节**：

1. **一句话结果**：你的场景现在能怎样了。

> 本节是 `07-DELIVERY-REPORT.md` 在对话式模式下的**摘要版**；完整技术版（证据表、命令、Release 链接）同时归档在后台 issue 评论，两者同源，摘要不得与完整版矛盾。
2. **怎么用**：最短的操作说明（通常 0–3 步；纯内部改动写「不需要你做任何事」）。
3. **我怎么验证的（人话）**：做过哪些检查、有没有故意使坏测试过、结论是什么。
4. **已知限制**：还没覆盖什么、什么情况下会不好用（诚实列出，不藏）。
5. **需要你决定 / 下一步**：需要你拍板的选择题，或「没有，等你验收」。

技术链接（PR、CI、Release）放在报告末尾作附录；业务方不看也不影响验收。

## 6. 什么时候 DSH 会回来问你（升级规则）

以下情况**必须**回到对话里确认（`09-ESCALATION.md`）：
- 不可逆操作（删数据、改历史、覆盖发布、改仓库可见性）；
- 涉及账号、权限、凭据、花钱、对外发布；
- 需求范围要做取舍（加功能 vs 延期 vs 砍需求）；
- 验收口径本身不清晰、或实现后发现原需求不成立。

不需要你决定的事（DSH 自行处理）：**在标准库或已批准依赖范围内**选型、怎么写代码、怎么测、怎么提交、分支怎么命名、文档放哪。
**新增第三方依赖或引入外部代码属于 `09-ESCALATION.md` E-04**：DSH 会停下来，给出来源、许可证、替代方案与影响，等你确认后再继续。
默认规则：可逆且低风险的事项，DSH 按最保守方案继续并在报告里说明；不可逆事项一律等你回复。

## 7. 记录与追溯（你不用管，但保证可查）

- 后台仍会创建 GitHub issue / PR / Release 作为**审计凭证**（合规、可回溯、可交接）；
- 过程证据保存在本机 `.agentspec/runs/<时间戳>/`（不进公开仓）；
- 跨会话续接：换一个会话也可以说「继续上次那个需求」；DSH 通过后台 issue 编号与交付报告恢复上下文，不依赖聊天记忆。

## 8. 安全边界（不会因为「对话式」而放松）

1. **门禁不削弱**：自动测试、独立评审、CI、分支保护照常执行；不通过就不合并。
2. **合并与发布由 DSH 代操作**：前提是门禁全绿 + 独立评审通过；**发布前会做一次 Go/No-Go 确认**——你回「发」才发，只告知不算确认。
3. **不碰凭据**：你不需要提供 GitHub token；本机已登录的 `gh` 凭据只在本地使用，不写进对话或仓库。**环境前提**：DSH 宿主机必须已登录 `gh` 且对仓库有 `repo` 权限；未满足时 DSH 停手并告知你（这是环境问题，不需要你处理技术细节，只需要决定是否授权修复环境）。
4. **隐私**：你的对话内容不会原样公开；写进公开任务单的只有必要的业务描述，且经过去敏。
5. **规则文件保护**：`.github/**`、`agents/**`、`docs/process/**` 的修改需要你**明确同意**，并留下可机械核查的批准记录：PR 打 `needs-human-review` 标签 + 一条评论**逐字引用你的原话**（含日期）。你不需要使用 GitHub 的 review 界面；**G5 仍由新上下文 reviewer 独立执行，不因对话式而取消**。

## 9. 与开发者模式的关系

| 模式 | 适用人 | 入口 | 说明 |
|---|---|---|---|
| **A 对话式（默认）** | 业务方、不懂开发的决策者 | 直接和 DSH 对话 | 本文件 |
| **B issue 式** | 开发者、贡献者、外部社区 | GitHub issue 表单 + `agent:ready` | `01-REQUIREMENT-INTAKE.md` |

两种模式共用同一后台（G0–G7、角色、CI、orchestrator）；对话式只是把「写 issue/看 PR/合并」这些机械动作交给 DSH 代办。

## 10. 反模式（别这样做）

- ❌ 在对话里贴密钥、密码、个人隐私信息 → 不要贴；需要时用本机配置。
- ❌ 一句话塞 5 个不相关需求 → 拆开说，DSH 会一次只推进一个。
- ❌ 一边让 DSH 做，一边自己手改仓库 → 会产生冲突；要改就说出来，让流程处理。
- ❌ 把「代码能跑」当成「业务目标达成」→ 验收看的是第 5 节报告里的结果与限制。
- ❌ 要求跳过测试/评审直接上线 → DSH 会拒绝并说明原因（门禁是保护你的）。

## 11. 最小人类参与（决策式，核心原则）

> 本模式的设计目标是：**人类只拍板「做不做」和「往哪个方向做」，其余全部由 AI 自驱动并自证质量。**

### 11.1 人类只做两类决定

| 决定类型 | 例子 | 形式 | 频率 |
|---|---|---|---|
| **Go / No-Go** | 要不要做这个需求；现在发不发版；这个风险接不接受；验收通过/不通过 | 对话里回「做 / 不做」「发 / 不发」「通过 / 不通过」 | 每个需求 1–2 次 |
| **Direction（方向）** | 方案 A 还是 B；先做哪一块；范围要不要砍；预算上限 | 选择题（A/B/都行/暂停），DSH 给默认项与影响 | 只在方向冲突时 1 次 |

除此之外的**技术决策一律由 AI 自行决定并记录**：架构怎么拆、测试怎么写、分支怎么命名、文档放哪、失败怎么重试、评审怎么组织——不再问人。
库/依赖选型不属于本条：只能在标准库或已批准依赖范围内选；新增第三方依赖按 §6 与 `09-ESCALATION.md` E-04 停下，给出来源、许可证、替代方案与影响，等 owner 确认。

### 11.2 AI 必须自设计工作流，而不是套模板

- 接到需求后，先由 **workflow-designer 角色**（`agents/roles/workflow-designer.md`）产出任务级 `PLAN.md`：3–8 个切片、每片写域与可执行验收命令、依赖关系、反例、回滚、人类决策点。
- **先跑红再动手**：每条验收命令必须先证明在当前代码上会失败（或说明为何无法跑红），否则不算验收。
- 默认流程适用时也要写明理由；不适用时允许 AI 改动工作流设计，但**门禁强度只能加强不能削弱**。
- 人类决策点必须在设计阶段就列出来（默认 ≤2），而不是执行中随机冒出来。

### 11.3 AI 自驱动的执行循环

```text
需求（对话/issue）
  → intake：BRIEF（需求摘要 + 验收口径 + 风险 + 非目标）
  → workflow-designer：PLAN（切片 + 验收命令 + 写域 + 反例 + 决策点）
  → 执行：隔离 worktree 中实现 → 每片验收 → 失败自动重试（≤2）→ 仍失败则停下并给证据
  → 质量保证：独立 verifier（新上下文复跑）+ reviewer（新上下文对抗审查）+ CI
  → 合并/发布：门禁全绿后由 AI 代办；发布前只做一次 Go/No-Go
  → 交付：5 段人话报告（第 5 节）+ 后台审计凭证（issue/PR/Release）
```

- 循环由 orchestrator / DSH 会话驱动；人类不参与中间步骤。
- 停止并问人的**唯一条件**：不可逆动作、风险超阈值、方向冲突、预算超限、验收口径不成立（见第 6 节与 `09-ESCALATION.md`）。
- 每个需求最多 **2 次**人类决策（默认：立项方向 + 发布前 Go）；验收本身是第 2 次。

## 12. 质量保证（AI 自证，不依赖人盯）

「人类少参与」不等于「质量靠运气」。质量由以下分层机制保证，全部机械可查：

| 层 | 谁做 | 判据 |
|---|---|---|
| L0 静态 | 实现者 + CI | 类型检查、lint/契约校验、schema 一致性 |
| L1 单元/契约 | 实现者 + CI | 测试全绿；新增行为有测试；反例能变红 |
| L2 集成 | 实现者 + CI | e2e / 适配器契约 / 门禁命令 |
| L3 场景 | 发布前套件 | `node scenarios/run.mjs`：模拟真人使用路径，11 条发布门禁 |
| L4 独立验证 | verifier（**新上下文**） | 不采信作者证据，复跑全部验收命令；YELLOW 必须声明 |
| L5 对抗评审 | reviewer（**新上下文**） | 反例/变异测试、范围越界、安全、回滚；给出 `VERDICT` |
| L6 发布后 | 发布后验证 | 干净 clone 复现 + Release 校验；未验证项写 `UNCOLLECTED` |

三条硬规则：

1. **写的人不验自己**：implementer / verifier / reviewer 必须不同上下文；verifier 与 reviewer 也不共享上下文。
2. **反例必须能变红**：每条关键门禁至少有一次「故意使坏 → 必然失败 → 还原 → 复绿」的证据，否则视为假绿。
3. **未验证就说未验证**：无法验证的（真实后端 live、缺凭据的路径）一律写 `UNCOLLECTED`，不得算 PASS。

人类只在这些质量机制**之外**做两件事：接受/拒绝风险，以及最终验收。
