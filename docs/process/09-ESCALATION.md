# 09 — 升级（Escalation）：什么必须问人

> 目标：把「agent 可以自己决定」和「必须人拍板」划成可判定的边界，并规定等待/超时的默认行为。
> 相关：`00-OPERATING-MODEL.md` §6 权限边界、§5 用户只做 3 件事。

## 1. 升级的三个通道

| 通道 | 用途 | 落点 | 响应时限 |
|---|---|---|---|
| **E-issue 评论** | 需要用户/Lead 决策 | issue 评论 + `status/needs-info` + @owner | 24h |
| **浏览器/终端阻塞** | 需要人工权限或不可逆操作 | 停手 + 写「阻塞原因 + 已尝试 + 需要什么」 | 立即 |
| **交付报告「待决策」段** | 不阻塞本版本、但需用户知晓的取舍 | 交付报告 §7 | 随交付 |

升级单必须含：**问题一句话 / 为什么必须人决定 / 可选项 A/B/C（含默认项） / 不决定的后果 / 时限**。缺任一项视为升级无效，由 pm 退回补全。

## 2. 升级矩阵（命中任一即必须问人，agent 不得自行决定）

| ID | 类别 | 触发 | 为什么必须人决定 | 默认动作 | 时限 |
|---|---|---|---|---|---|
| E-01 | **不可逆** | 删除/重写 tag、改 git 历史（filter/rebase 已发布提交）、删除仓库/分支保护、删除 Release 资产、批量删文件 | 无法自动回滚 | 停手，列出受影响对象与备份方案 | 立即 |
| E-02 | **破坏性 ABI/兼容** | 删除/改语义的 ABI 项、schema 破坏性变更、配置键语义变更 | 影响外部用户 | 停手，给出迁移方案与版本策略 | 24h |
| E-03 | **权限/凭据** | 需要新 scope（`gh auth refresh`）、新增 token、改仓库可见性、增删协作者、Actions 额度/计费 | 涉及账户安全与费用 | 停手，说明需要的最小 scope | 立即 |
| E-04 | **法律/许可证/隐私** | 引入第三方代码/依赖、改 LICENSE、公开含个人信息内容、外部数据上传 | 法律责任 | 停手，给出来源与许可证清单 | 立即 |
| E-05 | **安全默认放宽** | 改默认权限档、关闭 worktree 隔离、允许危险模式、日志打印更多字段 | 削弱默认安全 | 停手，给出风险与补偿措施 | 24h |
| E-06 | **门禁削弱** | 修改/删除 required checks、跳过测试、放宽断言、改 labels/workflow 使门禁可绕过、改 `agents/**` 或 `docs/process/**` | 规则本身被改动 | 停手，走「规则自修改」人工批准 | 24h |
| E-07 | **范围取舍** | 需求与工期/成本冲突、砍功能、拆 issue、改变验收口径 | 业务优先级只有用户知道 | 停手，给 A/B 方案 | 24h |
| E-08 | **预算/成本** | 模型调用成本超阈值、Actions 分钟将耗尽、需要付费资源 | 花钱 | 停手，给出预估用量 | 24h |
| E-09 | **决策冲突** | verifier 与 reviewer 结论冲突、RFC 与实现冲突、三方各执一词 | 需要仲裁 | 停手，附双方证据 | 24h |
| E-10 | **外部发布** | 切仓库 public、对外发公告、发 npm、改 Release 可见性 | 对外不可撤销 | 停手，列出检查单 | 立即 |

## 2.1 已知平台约束（不是升级项，但必须记录）

| 约束 | 现状 | 流程替代 | 解除条件 |
|---|---|---|---|
| 私有仓 + 个人免费账号无法配置分支保护 | `gh api -X PUT .../branches/main/protection` 返回 **403**（已实测）；`scripts/provision-github.sh` 打印 `WARN` 后继续 | 用 process-guard + CI required checks + §4 评审判据（PR 评论 `VERDICT: APPROVE`）替代；见 `05-REVIEW-MERGE.md` §4 | 转 public 后重跑 `bash scripts/provision-github.sh` |
| 单 GitHub 账号不能给自己的 PR 提交 APPROVE | `gh pr review --approve` 对本人 PR 失败 | G5 以 PR 评论 `VERDICT: APPROVE` 落地；reviewer 仍必须新上下文且非作者 | 第二维护者/独立账号到位后升级为标准 review |
| `dsh headless` 在 DSH 文件沙箱内无法启动 | 写 `$DSH_HOME/profiles/headless/cordis.yml` 被拒（`EPERM`） | 用 `--runner mock` / `--dry-run`，真实执行在沙箱外；见 `10-DSH-LOCAL-AGENTS.md` §4 | 在沙箱外终端运行或预创建可写 profile |

这些约束不构成升级（不需要人决策），但每次交付都必须在交付报告「已知限制」列出；**禁止**把它们当成“已启用保护/已评审”的证据。

## 3. 升级单模板（issue 评论）

```markdown
## 需要你决定 · E-0X <类别>

**问题**：<一句话>

**为什么必须你决定**：<不可逆/法务/权限/范围/预算/门禁>

**背景与证据**：
- <命令 + 退出码 + 关键输出>
- <相关文件/PR 链接>

**选项**：
- A（默认）：<动作> → 影响：<…>
- B：<动作> → 影响：<…>
- C（暂停）：等你进一步信息 → 影响：<阻塞 X 小时>

**不决定的后果**：<…>

**时限**：<YYYY-MM-DD HH:MM +08:00 前；超时按 §4 处理>

@<owner> 回复 `A` / `B` / `C` 即可。
```

## 4. 等待与超时策略

| 情形 | 24h 内无回复 | 72h 内无回复 |
|---|---|---|
| E-07 范围取舍、E-09 仲裁 | 采用**默认项 A**，在 issue 记录「超时采用默认 A + 时间戳」 | 仍未回复 → 保留 `status/needs-info`，本 issue 不再自动推进；进入交付报告「待决策」 |
| E-02/E-05/E-06 等可逆但需批准 | 不采用默认，保持 `status/blocked`（不可逆风险不适用超时默认） | 同上 |
| E-01/E-03/E-04/E-10 不可逆/法务/权限 | **永不超时默认**；保持阻塞，写入交付报告 | 同上 |
| E-08 预算 | 采用最省资源的默认（如 mock/离线档），并声明降级 | 同上 |

超时默认只在**可逆且低风险**时启用；启用必须同时满足：① 默认项可 revert；② 不涉及对外发布/凭据/法务；③ 已在 issue 明确写出默认项。三条缺一即阻塞。

## 5. 升级路径与角色

| 情况 | 升级给谁 | 形式 |
|---|---|---|
| 技术方案分歧 | Lead（仲裁） | issue 评论 + 双方证据 |
| 需求/范围/优先级 | 用户（owner） | issue 评论 @owner |
| 权限/凭据 | 用户 | issue 评论 @owner + 最小 scope 说明 |
| 安全/泄漏 | Lead + 用户（立即） | issue 评论 + 停止 push/发布 |
| 流程规则缺陷 | Lead | issue 评论 + 建议修改 `docs/process/**`（走 E-06） |

## 6. 升级记录（可审计）

每次升级写一条 JSONL 到 `.agentspec/runs/<iso>/escalations.jsonl`：

```json
{"ts":"2026-10-26T10:15:00+08:00","id":"E-07","issue":12,"role":"pm","question":"是否接受把文档更新拆到下一个版本","options":["A","B","C"],"default":"A","deadline":"2026-10-27T10:15:00+08:00","outcome":"default-applied"}
```

`outcome` 取值：`answered` / `default-applied` / `blocked` / `withdrawn`。交付报告 §7 必须与这些记录一致。

## 7. 反例（不算升级，不得阻塞）

| 情形 | 为什么不算 | 正确动作 |
|---|---|---|
| 不知道怎么实现 | 技术问题 | 查文档/试实现/写 RFC |
| 测试红了但原因已知 | 可自行修复 | 修复后重跑 |
| 需要选变量名 | 无需人决策 | 按仓库风格自行决定 |
| CI 排队慢 | 可等待 | 等待/重跑，记录 YELLOW |
| 想让用户帮忙跑命令 | 可自动化的不交人 | 自己跑，贴证据 |
